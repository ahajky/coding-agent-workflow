# 六阶段工作流

旧项目与新项目共用同一套执行机制，差别只在前期输入。

## 阶段总览

```
01 Discover 建立上下文
   │  旧项目：读入口文档、查目录、跑测试、梳理实现
   │  新项目：澄清想法、目标用户、核心问题、约束、MVP
   ▼
02 Design 分析设计
   │  需求边界、风险与未知项、方案比较、（必要时）小型技术验证
   ▼
03 Plan 拆解任务
   │  可执行可验证的小任务、依赖关系、验收标准、涉及文件
   ▼
04 Execute 实施记录
   │  改代码、跑测试、遇新信息就更新计划
   ▼
05 Verify 验证审查
   │  符合需求？测试/Lint/构建？副作用、边界、遗留问题？
   ▼
06 Close 沉淀交接
       更新长期文档、归档任务、标记未完成部分
```

## 各阶段的门槛

每个阶段都有"进入条件"和"退出条件"。**退出条件通过才进入下一阶段**；否则留在本阶段或回退。

### 01 Discover

- 进入：收到一个新任务或新项目。
- 退出：
  - 旧项目：已能说明现有实现、依赖、测试方式、风险点，以及"现状图"。
  - 新项目：已能说明目标、用户、核心问题、约束、MVP 边界。
  - 已列出"待确认事项"，需要人类决策的已明确标出。
- 产出：`brief.md`（任务简报 / 现状图）。

### 02 Design

- 进入：上下文足够。
- 退出：需求边界明确；风险与未知项已列出；方案已比较并有倾向；关键假设有验证或明确标注为未验证。
- 产出：`analysis.md`（必要时拆出 ADR 到 `.agent/docs/decisions/`）。
- 回退：若发现需求本身不清，退回 01。

### 03 Plan

- 进入：方案已定。
- 退出：任务已拆成可独立验证的小步；每步有完成条件与验收标准；依赖顺序清晰；已标注涉及的文件/模块。
- 产出：`plan.md`。

### 04 Execute

- 进入：计划已就绪。
- 退出：计划内的改动已完成；必要的测试已运行；偏离原计划的地方已记录并说明原因。
- 产出：代码变更、必要的实验记录、进度更新（写回 `handoff.md`）。
- 回退：发现架构/方案不支持预期需求 → 退回 02；计划不成立 → 退回 03。

### 05 Verify

- 进入：实施完成。
- 退出：对照需求逐条检查；测试/Lint/构建**真实执行**并记录原始结果；副作用、边界情况、遗留问题已列出；失败项标清失败原因。
- 产出：`validation.md`。
- 回退：验证失败 → 退回 04，必要时重新评估方案回到 02。

### 06 Close / Handoff

- 进入：验证通过，或已明确记录未完成部分。
- 退出：长期有效的结论已落到 `.agent/docs/`（团队共识再沉淀到项目文档）；`handoff.md` 能回答六个问题（见下）；结束的任务已移入 `.agent/work/archive/`。
- 产出：更新后的项目知识、任务结论、下一步建议。

## 交接必须能回答的六个问题

1. 实际完成了什么？
2. 修改了哪些关键文件？
3. 运行了哪些验证，结果如何？
4. 哪些问题还没解决？
5. 下一步最合理的行动是什么？
6. 需要人类决策或确认的事项有哪些？

这些信息必须进入持久化文件，而不是只出现在最后一条聊天消息里。

## 关于循环

流程是**可循环的**，不是单向流水线。任何阶段发现前提不成立，都应显式回退，并在 `handoff.md` 中记录回退原因。
