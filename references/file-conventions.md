# 文件与目录规范

## 目录树

```
my-project/
├── AGENTS.md                # Agent 入口（留在根目录，默认只在本机）
├── README.md                # 项目自己的总览
├── .agent/                  # 工作流目录（默认 gitignore，只给自己看）
│   ├── docs/                # 我的理解与决策
│   │   ├── product/         # 目标、需求（如 requirements.md）
│   │   ├── architecture/    # 架构、代码地图
│   │   ├── decisions/       # ADR（ADR-NNN-<标题>.md）
│   │   └── guides/          # 知识讲解、机制解释、场景说明、可复用步骤
│   ├── reports/             # 交付物草稿（定稿后再搬进项目）
│   ├── references/          # 外部参考资料（别人写的，只读）
│   └── work/
│       ├── active/          # 当前任务工作区
│       │   └── <YYYYMMDD-短语>/
│       │       ├── brief.md / analysis.md / plan.md / validation.md / handoff.md
│       │       └── scratch/     # 临时脚本与数据，随时可整目录删掉
│       └── archive/         # 已结束任务
├── docs/                    # 项目自己的正式文档（已有就沿用，没有不必建）
├── src/
├── tests/
└── scripts/                 # 项目里可复用的正式脚本
```

三件事要记住：

- **`.agent/` 是默认名**，可由 `AGENTS.md` front-matter 的 `workflow_root` 改（例如 `agent-work/`）。下文一律按默认名书写。
- **根目录 `AGENTS.md` 与工作流目录都是个人工作资产。** 默认不入库，见「Git 与工作流目录」。`gitignore` 不影响 Codex 读取这些文件。
- **项目自己的 `docs/` 不动。** 工作流不擅自往里写；用户要求维护正式文档或主动"沉淀"时按项目约定写入，见下一节。

## 为什么单独一个目录

把工作流产出混进项目结构里，会同时踩四个坑：

1. **受众不同。** 这些文档是给自己看的判断、草稿和踩坑记录，不是团队交付物。
2. **共识不能伪造。** 个人理解直接写进项目 `docs/`，会被后来的人当成已经讨论过的结论。
3. **提交会变脏。** 多人协作时，代码提交里混进个人笔记，Review 噪音大、冲突多、还可能夹带不该外流的信息。
4. **迁移成本高。** 单独一个目录，换项目、换机器、整份丢掉都只要一步。

代价也要说清楚：**不进项目 Git，就没有项目自带的历史与跨机器同步。** 需要时自己补（见「Git 与工作流目录」）。

## 与项目文档的边界：沉淀

`.agent/docs/` 里的东西默认**不外流**。要让某个结论成为团队知识，走三步：

1. **先讨论。** 结论要经得起别人质疑；没讨论过的，就还停在个人理解阶段。
2. **写进项目的正式位置**（项目自己的 `docs/`，或团队约定的地方），按那边的格式写。
3. **在原处留一条指针**，例如"已沉淀到 `docs/architecture/auth.md`"，或者直接删掉。

交付物同理：`reports/` 里是草稿，定稿后再搬进项目的交付目录；用户明确指定正式产物位置时可直接写入。

判据只有一句：**别人要看、要维护 → 项目文档；只有我用 → `.agent/`。这里的“别人”指共同维护或正式交付的受众，不包括给使用者本人解释知识的 Agent。**

## 外部资料：拷贝 + 索引

项目里的外部资料常常散落在 `docs/`、`vendor/`、网盘或聊天附件里，有的根本不在仓库中（已被 gitignore）。**工作流目录要能整体带走，就必须有一份可用的副本**，只留一个"指向项目别处"的路径是不够的。

但拷贝的是**工作副本**，原件仍然是权威。三条规则：

1. **只拷用得上的部分。** 整库搬运会把体积和噪音一起带进来；用不上的译本、示例数据、历史版本不必拷。
2. **必须登记来源。** 写进 `references/README.md`：名称、来源路径、导入时间、用途。没有索引的副本，过几个月就没人知道它从哪来、是不是最新的。
3. **不改原文。** 批注、摘要、结论写进 `.agent/docs/` 或任务目录；原件更新后重新导入。

用脚本导入，索引会一起更新：

```bash
scripts/import-reference.sh ../vendor-api-docs --note "第三方接口文档 v2.3"
```

**不要拷的**：超大二进制、含真实客户数据或密钥的材料、许可不允许再分发的文件。这类只在索引里写明"原件在哪、为什么没拷"，用时去原件看。

## 目录职责

| 位置 | 负责 | 不负责 |
| --- | --- | --- |
| `AGENTS.md` | 项目规则、目录导航、测试命令、任务路由（每次会话必读） | 不做百科全书，不记任务过程 |
| `README.md` | 面向人类的总览：这是什么、怎么开始 | 不写 Agent 规则 |
| `.agent/docs/` | 我对目标、架构、决策、操作的理解；可随时推翻 | 不作为团队共识；不复制项目已有的正式文档 |
| `.agent/reports/` | 交付物草稿与素材 | 不放定稿（定稿进项目） |
| `.agent/references/` | 外部资料的**工作副本**（只读）：规范、接口文档、论文；索引在 `references/README.md` | 不放我自己写的东西；**不改写原文**；不整份搬运与工作无关的内容 |
| `.agent/work/active/` | 任务的需求澄清、调查、方案、计划、验证、交接 | 不放正式测试/脚本 |
| `.agent/work/active/<任务>/scratch/` | 该任务的临时脚本、日志、抓包、中间数据（可整体删除） | 不放结论；不作为证据的唯一存放地 |
| `.agent/work/archive/` | 已结束任务的重要结论、关键过程、验证证据 | 不存临时日志、重复草稿 |
| 项目 `docs/` | 团队共识与正式文档 | 不记个人探索过程 |
| `src/ tests/ scripts/` | 正式代码、测试、可复用脚本 | 不作文档沉淀地 |

## 谁写的、给谁看

| 目录 | 谁写的 | 给谁看 |
| --- | --- | --- |
| `.agent/docs/` | 我自己 | 我自己（工作记忆） |
| `.agent/reports/` | 我自己 | 先是自己，定稿后才给别人 |
| `.agent/references/` | 别人 | 我自己（外部输入的工作副本） |
| 项目 `docs/` | 团队 | 团队与后续维护者 |

两条容易踩的规则：

- **`references/` 里的东西是证据，不要改写。** 要批注、要总结，写进 `.agent/docs/` 或任务目录。
- **草稿与定稿分开放。** 草稿在 `.agent/`，定稿搬进项目；搬完只在项目里维护那一份。

## 信息权威来源（唯一）

| 信息 | 权威来源 |
| --- | --- |
| 团队共识（目标、架构、决策、规范） | 项目 `docs/`（或团队约定的位置） |
| 我当前的理解与判断 | `.agent/docs/` |
| 外部参考资料 | 外部原件；`.agent/references/` 为只读工作副本，来源记在索引 |
| 任务的背景与调查 | `.agent/work/active/<任务>/brief.md`、`analysis.md` |
| 某任务如何实施 | `.agent/work/active/<任务>/plan.md` |
| 任务的测试与验收结果 | `.agent/work/active/<任务>/validation.md` |
| 当前进度与下一步 | `.agent/work/active/<任务>/handoff.md` |
| 代码是什么样、怎么变成这样 | 代码仓库的 Git 历史 |
| 历史会话原文 | Agent 自身的会话记录系统 |

关键区分：

- **已沉淀的事实以项目文档为准**，`.agent/docs/` 里留一条指针，不再复述。
- **尚未沉淀的，`.agent/docs/` 就是唯一权威**——别在两个地方各写一半。
- 任务文档记录过程；同一结论要长期保留，就沉淀到 `.agent/docs/`（个人）或项目文档（团队）。

## 任务目录命名

格式：`YYYYMMDD-<短横线短语>`，例如 `20261010-add-auth`。

- 以**日期 + 短语**为主键，避免多个 Agent 并行时撞号。
- 需要人工排序时可在前面加顺序号（`2026-001-add-auth`），但冲突时**以日期 + 短语为准**，不要求全局唯一。
- 短语用小写英文、短横线分词，说明任务主题。
- **日期由脚本兜底**：`init-task.sh .agent/work/active/add-auth` 会自动建成 `20261018-add-auth`，并提示改名了；已经带日期前缀则原样使用。`check-project.sh` 会对缺日期前缀的任务目录发出提醒。

## 文档写入前的归属判断（权威规则）

适用于 Agent 新建、更新、整理、导出文档的请求。按用途和维护责任判断，不按“说明”“报告”等标题或 Markdown / PDF / Word 等格式判断。下表按默认 `.agent/` 书写，实际路径服从 `AGENTS.md` 的映射。

### 判断顺序

1. **用户明确指定路径或项目已有正式位置时，优先遵循。** 修改现有 README、API 文档、运行手册等，直接更新原件；用户明确要求创建正式文档也可直接写入约定位置，无须先造一份个人草稿。个人探索结论自行升级为团队共识时，仍须经过讨论与沉淀。
2. **先查同主题的现有文档。** 已有权威文档就补充原件，其他位置只留链接；外部原文保持只读，摘要与批注另存。
3. **没有既定位置时，按下表选择。** 同时涉及多个用途时，以主要用途确定唯一正文位置，其余位置链接；只有内容各自独立、维护周期不同才拆分。
4. **写入前确认具体文件路径。** 不得把根目录、`docs/` 或 `reports/` 当作未分类收纳箱。回复中提供实际产物链接；存在相关任务时，写入 `handoff.md` 的 References。

### 常见需求覆盖表

| 文档需求 | 默认归属 | 边界 |
| --- | --- | --- |
| 知识讲解、术语解释、机制原理、代码阅读说明、场景推演、FAQ、操作与排障指南 | `.agent/docs/guides/<主题>.md` | 面向用户理解与复用；整体结构与模块关系进 architecture |
| 项目目标、产品构思、跨任务需求梳理、用户场景与验收规则 | `.agent/docs/product/` | 当前任务范围与验收条件进 brief / plan |
| 系统设计、架构图、模块关系、数据流、代码地图、接口设计草案 | `.agent/docs/architecture/` | 当前任务的备选方案与取舍进 analysis |
| 已作出的长期决策及理由 | `.agent/docs/decisions/ADR-*.md` | 仍在比较的方案进 analysis，不伪装成已定决策 |
| 单次需求澄清、调查、方案比较、技术选型、实验结论 | 当前任务的 `brief.md` / `analysis.md` | analysis 也覆盖无需比较方案的调查与诊断 |
| 实施、迁移、发布、回滚的本次执行计划 | 当前任务的 `plan.md` | 可复用操作规程进 guides；正式运行手册按项目位置 |
| 本次测试、验收、性能验证的结果与证据 | 当前任务的 `validation.md` 及证据附件 | 需要留存的证据放任务目录的 `evidence/`，不能只放 scratch |
| 单次评审、审计、故障复盘、会议纪要、讨论记录 | 当前任务的语义文件，如 `review.md`、`incident.md`、`meeting.md` | 决策和长期说明分别提炼到 decisions / guides，原记录保留链接 |
| 当前进展、待办、阻塞、交接 | 当前任务的 `handoff.md` | 项目总览只链接任务，避免维护第二套进度 |
| 对外报告、演示稿、提案及其素材 | `.agent/reports/<主题>/` | 面向交付；用户指定交付路径优先，定稿后只维护正式原件 |
| 外部规范、论文、用户提供的材料 | `.agent/references/` 与来源索引 | 工作副本只读；自己的摘要、翻译、批注按用途进 guides 或任务目录，并链接原件 |
| 临时提纲、重复草稿、原始调试日志、可丢弃的中间文件 | 当前任务的 `scratch/` | 有价值的结论与验证证据移出后才可清理 |
| README、API 文档、发布说明、贡献指南、团队规范、正式用户手册 | 项目已有或明确指定的正式位置 | 按项目维护责任与格式写入；不强制经过个人草稿 |

### 轻量说明、格式与维护

- 用户只要求聊天解释时，默认在聊天回答；明确要求“写一份文档”“保存说明”时才落盘。影响后续项目工作的结论仍按保留策略持久化。
- 单份可复用知识说明可直接写入 guides，无须为了存放它新建任务；若已有相关任务则回链。多步研究或实施工作仍建立任务工作区。
- 指南开头简述面向谁、解决什么问题、适用范围；依赖项目代码或外部材料时标明相关文件或来源。更新时检查前提是否仍成立；过时内容修订或标记失效，不再并列维护“新版副本”。
- 图片、图表、PDF、Word、演示稿、表格与正文按同一用途归类，附件就近放在主题子目录。可编辑源文件与导出文件可并存，但注明源文件，导出件不独立编辑。
- 任务归档时修正链接；将正文迁到长期位置后，原处只留指针，避免路径变化造成不可恢复的断链。

## 规范外的产物怎么办

目录树是默认约定，不是白名单。未命中覆盖表时，先确定受众、用途、维护责任和保留期限：属于任务的放任务目录；需要跨任务复用的在 `.agent/docs/` 下按主题扩展；面向交付的进 reports；外部输入进 references。

新增长期分类或工作流顶层目录时，必须在 `AGENTS.md` 的目录导航中登记路径、用途与维护责任；主题子目录、任务文件与附件无需逐个登记。确实仍无法判断且会影响共享或维护责任时，向用户澄清；不为每个文件机械询问。

## 归属约束的能力边界

`AGENTS.md` 的会话检查与写入前规则提供行为约束，`handoff.md` 的链接提供追溯。当前 `check-project.sh` 仅检查目录、部分入口内容、任务状态与 Git 约定，**不会判断文章用途、发现全部错放文件、验证全部链接或阻止越界写入**。检查通过不等于文档归属正确。

人工或 Agent 收工检查必须核对：本次每份新增文档有明确归属；已有权威内容未被重复维护；相关任务有产物链接；新增分类已登记。若项目要求强制门禁，需另行接入文档清单与路径白名单的 hooks / CI；语义归属仍需评审，不能仅靠文件名判断。

## Git 与工作流目录

默认约定：**根目录 `AGENTS.md` 与整个工作流目录（`.agent/`）都不进项目版本控制。**

- 代码提交只包含代码与项目正式文档，不出现个人笔记、任务草稿、交接文件。
- 任务对应哪个代码分支，写在 `handoff.md` 的 `branch` 字段里——工作流目录虽然在仓库外，这条线索仍然在。
- `init-project.sh` 会把 `AGENTS.md` 和 `.agent/` 都写进 `.gitignore`；`check-project.sh` 发现它们可能进入 Git 时会提醒。
- `AGENTS.md` 必须留在项目根目录，这是工具发现规则的位置要求；是否进入 Git 与它放在哪里无关。默认只给自己使用时忽略它；确认团队也要共用这套规则时，再显式取消忽略并提交。

如果你确实想让工作流也有版本历史（个人项目、或想跨机器），两种做法：

- **去掉 `AGENTS.md` 和 `.agent/` 的 gitignore**，让它们跟着项目走——代价是团队仓库里会出现你的个人工作内容；
- **把 `.agent/` 单独做成一个仓库**（它自己的 `.git`），项目仓库依然忽略它。推荐这种：历史独立、代码库干净。

代价要认：不入库就没有项目自带的历史与同步。跨机器时靠自带仓库、网盘或同步工具补，这是"只给自己看"换来的清净。

## 占位符约定

- `<...>` 表示**待填**：必须替换成真实内容，或整行删掉。`check-project.sh` 会扫描"整行就是占位符"的行并提醒。
- `（...）` 只用于句中的补充说明，**不要**用它充当占位符。
- 提交到项目仓库的内容不该留下未填的 `<...>`。

## 任务目录的文档

每个任务都建这三个文件。**内容可长可短**——简单任务写一两句也算，不要为了凑格式而灌水。

| 文档 | 负责 | 什么时候写 |
| --- | --- | --- |
| `brief.md` | **这任务是什么**：为什么做、边界、明确不做的事、约束 | 任务开始时写一次 |
| `plan.md` | **打算怎么做**：步骤、验收标准、打算怎么验证 | 计划阶段写，实施中可修订 |
| `handoff.md` | **现在到哪了**：状态、卡点、下一步 | 每次收工都更新 |

以下文档**有明确触发条件才建**，不要为了齐全而建：

| 文档 | 触发条件 |
| --- | --- |
| `validation.md` | 需要留下验证证据时（通常只要跑过测试就该写） |
| `analysis.md` | 调查、诊断、实验或方案比较需要留存时 |
| `.agent/docs/decisions/ADR-*.md` | 产出了需要长期保留的决策时 |

判断依据是**单份文档的用途**，不是任务的"大小"。任务不分类别，也就没有分错的可能。

## `AGENTS.md` 应包含

`AGENTS.md` 是协议的**常驻入口**（Skill 可能不被触发，但 `AGENTS.md` 每次会话都会读）。它的四条铁律、必备内容与嵌套约定，见 [agents-md.md](agents-md.md)。模板见 `templates/AGENTS.md`，可用 `scripts/init-project.sh` 生成。
