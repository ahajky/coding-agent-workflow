# AGENTS.md：协议常驻入口

## 为什么它比 Skill 更关键

Skill 是**按需加载**的，可能不被触发；`AGENTS.md` 在每个会话里都会被读取。所以工作流能否"自己活下去"，取决于 `AGENTS.md` 里有没有写下最小铁律。

一句话：**`AGENTS.md` 是底线版，Skill 是展开版。** 底线保证协议不会因为 Skill 没触发而整体失效。

默认工作流只给使用者本人使用，因此 `AGENTS.md` 虽然必须位于项目根目录，也应写入 `.gitignore`。Git 忽略不影响 Codex 从本地读取它；只有团队确认要共同维护这套规则时，才显式提交。

## 必须包含的四条铁律

1. **开工先恢复上下文**：每次会话开始项目工作前先核对入口的路径映射和文档归属规则，再看 `.agent/work/active/` 有没有相关任务，有就读 `handoff.md` 并据此继续，不重新分析、不覆盖已有成果。
2. **收工必写回状态**：完成或中断前更新 `handoff.md` 的 `status`、`Completed`、`Current State`、`Next Actions`、`updated`。
3. **尊重信息归属**：任务过程留在 `.agent/work/active/<任务>/`，个人理解进 `.agent/docs/`；这些是个人工作记忆，不直接写进项目正式文档，成为团队共识要经讨论后沉淀。
4. **不写敏感信息**：不出现密钥、token、密码、内网地址、客户个人数据。

这四条对**所有规模的任务**都生效，包括"小修"。任务的 brief / plan / handoff 均建立，内容可短。单份可复用知识说明可直接写入 guides，无须为存放它新建任务。

## 文档归属约束

入口必须包含精简的写入前路由：知识与场景说明进 `docs/guides/`，任务记录进任务目录，对外交付草稿进 reports，外部输入进 references；用户指定路径和项目已有正式位置优先。要求先查原件、写前确认路径、收工检查归属并回链。完整覆盖表以 [file-conventions.md](file-conventions.md) 为权威，不在入口复制全文。每次会话恢复时核对入口，后续按需读取细则，无须每轮消息重读全部文档。

仅有入口文本不能强制保证归属正确；现有脚本不做语义分类，收工须审查本次新文档。

## 还应包含

- 项目定位（一句话）。
- 路径映射：`workflow_root`（默认 `.agent/`），脚本按它读取。
- 目录导航：去哪找需求、架构、决策。
- 常用命令：安装、测试、检查、运行。
- 任务路由：不同类型任务先读哪些文档。

保持精简，指向细节而不是复制细节。完整流程、阶段门槛、模板都在 `coding-agent-workflow` 技能里。

## 嵌套约定（monorepo / 子项目）

子目录可以放自己的 `AGENTS.md`，更具体的那份覆盖父级。子文件只写与根不同的部分即可。

（v1.1 只约定这条规则，暂未提供多文件生成工具。）

## 校验

`scripts/check-project.sh` 会检查 `AGENTS.md` 是否存在，并粗查它是否提到了 `handoff`（提醒是否写了第 1、2 条铁律）。

## 升级检测

新入口的文档检查段包含会话开始时的升级检测；新项目初始化会登记规则版本与基线。已接入项目需先运行一次 `scripts/update-project.py` 预览，再以 `--apply` 接入，之后可随会话检测更新。尚未接入的旧入口不会凭空获得新指令，须由用户或已加载的新 Skill 触发首次升级。同步边界、状态目录与冲突处理见 [upgrade-protocol.md](upgrade-protocol.md)。
