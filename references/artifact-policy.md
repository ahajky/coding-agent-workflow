# 中间产出保留策略

不要把所有中间产出都保存下来。判断标准只有一条：

> 它能否降低未来某人的理解成本、决策成本或重复劳动？

## 三级保留

| 级别 | 内容 | 保留判断 |
| --- | --- | --- |
| **A 必须持久化** | 项目目标、有效需求、重要架构决策、当前任务状态、验收结果、未解决风险 | 丢失它，未来可能做错决策或重复大量工作 |
| **B 有价值时保留** | 方案对比、技术调查、性能实验、复杂 Bug 排查过程、被否决但值得记录的路线 | 能解释不直观的决定，或帮助排障、避免重复试错 |
| **C 默认不保留** | 重复草稿、无信息增量的中间推理、短期调试输出、失效临时文件 | 对未来没有足够价值 |

## 决策记录 vs 过程记录

- **决策记录**（通常长期保存）：结论、背景、考虑过的方案、主要取舍、后果。见 `templates/adr.md`。
- **原始过程记录**（按需保存）：完整终端输出、临时调试日志、实验文件。优先靠 Git 历史、测试结果或外部日志追溯；确需保留时放进任务目录并标注用途。

## 落到哪里

| 产出类型 | 去处 |
| --- | --- |
| 知识讲解、机制解释、场景说明、FAQ | `.agent/docs/guides/`；已有同主题文档则更新原件 |
| 对外交付草稿与素材 | `.agent/reports/<主题>/`；明确指定的正式交付位置优先 |
| 长期结论（需求、架构、决策） | `.agent/docs/`；已成团队共识的沉淀到项目文档 |
| 任务过程（简报、分析、计划、验证、交接） | `.agent/work/active/<任务>/` |
| 外部参考资料 | `.agent/references/`（工作副本，来源记在 `references/README.md`；大体积或敏感材料只留指针） |
| 可复用的自动化 | `scripts/` 或项目正式脚本目录 |
| 正式测试 | `tests/` |
| 临时草稿、验证脚本、日志 | `.agent/work/active/<任务>/scratch/`（任务归档时整体丢弃） |

完整归属判断与覆盖表以 [file-conventions.md](file-conventions.md) 为准。用户明确要求保存的说明应持久化，不因“不属于需求或决策”而丢弃。

## `scratch/`：临时的唯一去处

`.agent/work/active/<任务>/scratch/` 是该任务临时产物的唯一去处：验证脚本、日志、抓包、中间数据。工作流目录整体不入库，**随时可以整目录删除**。

- 验证脚本写在里面。**同一个脚本写到第二次，就搬进 `scripts/` 并提交**——是否需要长期保留，用"重复"这个客观信号判断，不必评估价值。
- 清理时机跟随任务：任务归档时一并处理，不另设流程。
- 它**不得**作为任务证据的唯一存放地；任务需要的证据，须移到任务的 `evidence/` 并在 `validation.md` 或 `analysis.md` 中链接，或把关键证据直接写入这些文档；仅引用 scratch 中的文件不能保证清理后仍可恢复。

## 红线：不许写进文档

工作流目录默认不入库，但它会被整份备份、同步或分享，沉淀到项目文档时还会进仓库。以下内容**一律不写**：

- 密钥、token、密码、私钥、API key
- 内网地址、账号、连接串
- 客户 / 用户的个人数据
- 未脱敏的生产日志或真实数据样本

需要引用时写"见某处的环境变量 / 密钥管理服务"，而不是把值抄进文档。

## 反模式

- 强迫每个任务产出全套文档 → 制造噪音，Agent 为填模板而编造内容。
- 把分析结论只留在聊天里 → 换对话即丢失。
- 同一份信息在多处维护 → 半年后出现多个版本。
- 长期保存原始日志 → 淹没真正有价值的记录。
- 把密钥、内网地址、客户数据当"参考资料"写进文档 → 一旦入库难以清除。
