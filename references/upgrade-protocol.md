# 已有项目工作流升级协议

## 问题与边界

Skill 文件随安装更新，AGENTS.md 却是项目初始化时的快照。入口混合了通用规则与项目配置，重新运行初始化又不会覆盖原件，因此需要可审查的同步机制。

本轮采用章节基线方式，只管理模板中的「工作流铁律（必须遵守）」和「文档写入前检查」。这两节是一致的通用规则，项目补充应放在其他独立章节中。项目定位、front-matter、命令、目录导航、Git 约定、任务路由及其他自定义章节逐字保留。既有任务、知识文档、README、Git 跟踪策略与 hooks 均不自动修改。

常规同步只更新两节通用规则。1.x 的 tasks_root/docs_root 布局使用单独的 `migrate-project.py` 预览与迁移，详见 [归档与迁移](archive-and-migration.md)；自定义规则、导航、混合文档归属仍需审查。

## 版本与基线

- 技能根目录 `VERSION` 是目标版本的权威来源；协议版本头与变更记录随发版同步。
- 项目的 `<workflow_root>/.workflow/state.json` 保存 schema、上次同步的版本、路径和两节通用规则的实际内容。
- 此处版本表示“两节通用规则已同步到该版本”，不表示所有项目文件已迁移。
- 无状态时显示“未知”，不根据目录或部分文字推断整个项目的历史版本。
- 2.0.0—2.0.3 的原始通用章节收录在 `legacy-workflow-rules.json`（来自相应 Git 模板），允许识别未被修改的历史规则。模板外的写法、删掉的铁律或已定制的通用章节不会被猜测替换。

`.workflow/` 是本地升级元数据，随工作流目录一起忽略。它包含入口备份，继承工作流的访问与保密边界；不包含密钥。不要单独编辑状态文件以伪装升级成功。

## 检测、预览与应用

需要 Python 3.9+，无第三方依赖，命令中的脚本路径必须指向已更新的技能。

```bash
python3 /path/to/skill/scripts/update-project.py /path/to/project --check
python3 /path/to/skill/scripts/update-project.py /path/to/project --sync
```

1. `--check` 只检测：0 当前，3 有更新，2 有冲突，1 输入或状态错误。
2. 默认模式显示版本、workflow_root 与统一差异，不创建文件或目录。
3. `--sync` 再次计算并检查修改；全部受管章节无冲突才应用。不允许部分成功后把版本标为已更新。
4. 首次接入无文字差异时，仍需登记状态，因此检测会提示更新；再次执行没有变化则不重复写入或产生备份。
5. 不允许用较旧技能静默降级已登记的项目；需要撤销时使用备份回滚。

新项目的 init-project 会自动登记；已有 AGENTS 时初始化只提示同步命令，不覆盖原件。新版入口与 Skill 的恢复流程每次会话开始项目工作时调用 `--sync`；不必每轮聊天重复检查。同步使用当前本地技能目录，不自动 git pull；远程环境先由维护者更新技能仓库。check-project 只检查，不写入。

旧入口本身没有新检测指令，首次接入须用户主动运行，或在新版 Skill 被加载时触发。没有后台扫描、定时更新或跨项目批量修改。Python 缺失或检测失败时保留当前入口，如实报告，继续不依赖升级的工作。

## 合并规则与冲突

有基线时：本地章节等于旧基线，才能换成新版；已等于目标章节可直接接纳。其他情况冲突，包括本地删除受管章节。

无基线时：铁律必须等于已收录历史模板或当前模板；缺少文档写入检查可补充，已有该节则也必须匹配历史或当前模板。未知通用规则不能直接覆盖。

冲突时退出 2、展示本地与目标差异，入口和元数据均不写入。将项目补充移到独立章节，审查通用规则后手工合并到当前模板内容，再重跑工具以建立新基线。如果旧规则与新规则的含义不能判断，向使用者澄清；不要为了让脚本通过而删除约束。

目录导航不会自动合并；例如 guides 的旧描述仍可能保留，但新增通用路由明确知识与场景说明的去处。项目若曾修改路径，须确认导航与实际目录一致后再采用；工具只支持一个 workflow_root，不能自动理解所有项目私有映射。

## 备份与回滚

每次实际应用前，在 `.workflow/backups/<编号>/` 保存原始 AGENTS 字节、旧状态（若存在）与前后 SHA-256。应用以同目录临时文件替换，尽量保留入口权限；正常写入失败时尝试恢复。进程被强制杀死或机器断电时，可能需要使用备份人工恢复，不能承诺多文件事务。

```bash
python3 /path/to/skill/scripts/update-project.py /path/to/project --restore <备份编号>
```

回滚要求当前入口和版本状态都等于该次应用后的哈希，且备份校验通过；否则拒绝覆盖升级后新增的编辑。回滚恢复入口和旧状态，保留备份供审查，不回滚任何任务、项目文件或整个工作流目录。存在多次升级时从最近一次逐步回滚。

同一项目只允许一个升级写者；工具会在写入前核对原件，但没有跨进程锁，不能替代工作流的一写者约定。备份保留供使用者自行清理，工具不自动删除。

## 测试与后续

`scripts/tests/test_update_project.py` 使用临时真实目录与子进程验证升级、预览零写入、路径与任务保留、后续版本更新、冲突、幂等、备份完整性和回滚保护。

1.x 保守迁移已提供单独工具；后续可扩展独立受管块、导航与 Git 策略的三方合并及完整全项目语义校验。这些必须另有明确迁移规则和测试，不能通过扩大覆盖文件范围直接实现。


## 与技能版本更新的关系

本地软链接项目直接读取当前技能目录；技能文件更新后，下一次项目会话的 `--sync` 会比较目标通用章节并安全应用。远程技能副本必须先由维护者执行 `git pull`（或部署新版本），然后再运行同步。旧入口若没有新版 Skill 或新的检测指令，不会自发更新；首次接入由新版 Skill 或用户主动运行工具触发。Git 更新成功不等于所有项目已更新：每个项目仍需同步、处理冲突，1.x 目录迁移需单独运行 `migrate-project.py`。
