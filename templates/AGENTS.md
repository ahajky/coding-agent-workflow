## 工作流铁律（必须遵守）

本项目使用「编程 Agent 协作工作流」。以下四条不可省略：

1. **开工先恢复上下文**：每次会话开始项目工作前，先核对本文件的路径映射与目录归属规则，再看 `.agent/work/active/` 下是否有相关任务目录；有就读它的 `handoff.md`，据此继续，**不要重新分析、不要覆盖已有成果**。
2. **收工必写回状态**：任务完成或中断前，更新 `handoff.md` 的 `status`、`Completed`、`Current State`、`Next Actions`、`updated`。
3. **尊重信息归属**：任务过程留在 `.agent/work/active/<任务>/`，我的理解与决策留在 `.agent/docs/`；**这些是个人工作记忆，不直接写进项目正式文档**。要让它们成为团队共识，经讨论后搬过去，并在原处留一条指针。
4. **不写敏感信息**：文档中不出现密钥、token、密码、内网地址、客户个人数据。

重活（新功能、重构、调研）按六阶段推进：发现 → 设计 → 计划 → 实施 → 验证 → 交接；任务均建 brief / plan / handoff，内容可以很短，但**第 1、2 条不豁免**。完整规则见 `coding-agent-workflow` 技能。

## 文档写入前检查

- 每次会话开始项目工作时，若 `coding-agent-workflow` 技能可用，先用该技能目录下的 `python3 scripts/update-project.py <项目根> --sync` 同步入口；工具会展示差异、保存回滚原件并仅应用无冲突的通用规则，有冲突先合并，禁止整份覆盖入口。没有技能或 Python 3.9+ 时沿用当前规则并说明未检测。
- 用户明确指定路径、修改现有文档或要求正式文档时，遵循指定位置与项目约定；其余按以下默认归属写入。先查同主题原件，优先更新，避免复制维护。
- 知识、机制、场景说明与 FAQ → `.agent/docs/guides/`；长期目标需求 → `docs/product/`；架构与代码地图 → `docs/architecture/`；长期决策 → `docs/decisions/`（后三者同样位于工作流根目录）。
- 当前任务的调查、计划、评审、复盘、会议记录与验证证据 → `.agent/work/active/<任务>/`；临时可丢弃产物 → 该任务的 `scratch/`；需保留的证据放 `evidence/`。
- 对外交付草稿 → `.agent/reports/`；外部原文 → `.agent/references/` 并登记来源，自己的解释与摘要按用途另存。
- 按用途归类，与文件格式无关。混合用途选一个权威正文位置，其余留链接。源文件与导出文件注明关系。
- 仅聊天解释无需建文档；单份可复用说明可直接存 guides，无须为存放它新建任务。新增长期分类须在目录导航登记路径、用途与维护责任。
- 写入前确认具体路径；收工时核对本次所有新文档的归属与链接，相关任务的 handoff References 须回链；回复提供实际产物链接。

详细覆盖表与例外见技能的 `references/file-conventions.md`「文档写入前的归属判断」。这些是行为约束，当前检查脚本不自动判断文档语义或全部错放情况。

## 目录导航

以下路径都在 `workflow_root`（默认 `.agent/`）下：

| 位置 | 内容 |
| --- | --- |
| `docs/product/` | 我对目标与需求的理解（待团队确认的写在最前） |
| `docs/architecture/` | 我梳理的架构与代码地图 |
| `docs/decisions/` | 我认可的决策与理由（ADR） |
| `docs/guides/` | 知识讲解、机制解释、场景说明、FAQ 与可复用步骤 |
| `reports/` | 交付物草稿（定稿后再搬进项目正式位置） |
| `references/` | 外部资料的**工作副本**（只读；来源与导入时间记在 `references/README.md`） |
| `work/active/<任务>/` | 当前任务工作区（含 handoff.md） |
| `work/archive/` | 已结束任务 |

> 本表是**实际路径的权威**。改了上面的 `workflow_root`，这里的路径同步改。

## Git 约定

基准规则见 `coding-agent-workflow` 技能的 `references/git-workflow.md`。本项目必须遵守的只有这几条：

- 一任务一分支：`<type>/<任务目录名>`；单文件小修与纯文档改动可直接提交 `main`。
- 提交：`<type>(<任务目录名>): <说明>`，一个提交只做一件事。
- 不改写已推送的历史（rebase / amend / force push），合并用 `merge`。
- **`AGENTS.md` 与 `.agent/` 默认都不进版本控制**：代码提交里不出现这套个人工作流的内容。任务对应哪个代码分支，写在 `handoff.md` 的 `branch` 字段里。

本项目特有的补充约束（PR 流程、发布、评审等）写在本节下面，不要改基准。

## 任务路由

- 修 Bug：先读 `.agent/docs/architecture/` 下的架构与代码地图，以及相关任务的 `handoff.md`。
- 加功能：先读 `.agent/docs/product/`（需求）和 `.agent/docs/architecture/`（架构）。
- 重构 / 迁移：先读 `.agent/docs/decisions/`，确认既有约束再动手。

具体文件名由本项目自行约定；某份文档还没建立，先补再动手。
